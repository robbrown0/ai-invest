# Independent Cross-Author Security Review

**Status:** DRAFT — Design Gate 1 review, not implementation certification or human approval.

**Reviewer:** Security/data specialist acting as an independent reviewer of the other authors' integrated design, 2026-09-08.

**Purpose:** Challenge the completed architecture, execution, research, UX and test plans before opening the draft pull request.

## Scope and limits

Read the proposed architecture, all ten DRAFT ADRs, operations, full risk/execution design, UX storyboards, AI/expert contracts, experiments, model governance, P0/P1 requirements, test/UAT plans and initial backlog. Compared them with security/data/threat documents. This is cross-author virtual review: it is not independent human security review, a penetration test, a broker contract test, or proof that planned controls work.

Read-only change inspection showed documentation paths only at review time. Main-agent completion checks separately own Markdown/Mermaid validation, repository secret scanning and final diff verification. No application/service configuration was exercised and no real credential was inspected or provisioned.

## Actionable findings

Severity indicates the consequence of implementing the inconsistent design literally; no deployed vulnerability is alleged. Open Critical/High implementation findings would block release under AGENTS.md. The findings below must be resolved in the documentation or explicitly remain an unpassed design requirement; planned tests alone do not close a design contradiction.

| ID / severity | Finding and affected file | Required correction | Review status |

## Responses to the fourteen final-review questions

| Question | Assessment | Evidence or remaining gate |
| --- | --- | --- |
| 1. Could unauthorized real-money execution occur? | No live path is proposed or implemented; V0 must lack live endpoint/credential/adapter/promotion capability. This does not constrain a privileged human replacing the software outside scope. | ADR-0006/0010, no generic broker OAuth, mode/egress/credential qualification and ADV-23. Future live requires new design/human authorization. |
| 2. Could one tenant access another's information? | A concrete shared-role context hazard was identified. RLS plus application checks is conditional on independently authenticated tenant context and narrow roles, not raw SET. Host/global issuer compromise remains residual. | ADR-0004, ISR-03, two-tenant actual-runtime DB/API/job/export/cache tests before tenant data. |
| 3. Could compromised Internet research trade directly? | Architectural routes/credentials/approval authority are denied to ingestion and inference. Plausible poisoning may still influence an allowed proposal. | Source/parser isolation, bounded schemas, deterministic risk and TM-04 through TM-08; runtime network tests required. |
| 4. Could an LLM obtain brokerage credentials? | Inputs and environments must exclude them; broker reads remain in execution when credentials are order-capable. Debug/config/secret-zero paths remain important implementation proof points. | Allowlisted projection, execution-only OpenBao policy, synthetic-canary and denied-mount/egress tests. |
| 5. Could ambiguous/duplicate requests create duplicate trades? | Durable identity, one active intent and UNKNOWN reconciliation are appropriate, but lease-fencing assurance required correction. Remote exactly-once is not promised. | ISR-02, RISK_MODEL timeout/lookup rules, stale-worker and crash/restart simulator corpus. |
| 6. Can financial actions be reconstructed? | Proposed actor/source/proposal/risk/intent/fill chain is complete conceptually. Licensing-limited sources and a wholly local mutable audit chain limit proof. | Atomic audit/outbox, immutable versions, retained permitted evidence, independently archived checkpoints; restore/tamper tests. |
| 7. Are infrastructure/API costs unnecessary? | No paid service or continuous API is required. PostgreSQL jobs and one local inference queue avoid extra infrastructure; premium manual cost is explicitly allocated. | Cost/experiment ledgers; no paid fallback; local compute still needs measured resource budgets. |
| 8. Can it run on the local Ubuntu development host? | Plausible for serial local inference and modest private PAPER workloads, not verified. Keycloak/TDE/GPU contention and encrypted storage feasibility are gates. | Operations qualification and ADR-0001/0002/0008/0009; no unsupported VRAM-fit or HA claim. |
| 9. Can it support future commercial tenancy without fundamental rewrite? | Tenant ownership, interfaces, scoped ledgers and provider boundaries avoid a single-user core. Commercial assurance may require different isolation/key hosting and legal/operational controls. | Conceptual schema, composite keys, export/retention model; no promise that V0 is ready for customers. |
| 10. Does it test AI value rather than assume it? | A/B/C/D, preregistration, paired/fair timing, historical model-contamination limits, missingness and net external costs address the core question. | Experiment protocol; future power/regime-duration decisions and forward outcomes, no short-period edge claim. |
| 11. Are quantitative tasks separated from reasoning? | Arithmetic, scanning, portfolio metrics, account state and hard risk belong to deterministic/statistical processing. Models do bounded evidence interpretation and critique. | AI role table, model governance and ablations; add specialists only with measured contribution. |
| 12. Can a human understand proposed/allowed/rejected actions? | Evidence/bull-bear/cutoff/provenance and authoritative risk reasons are designed. Preview-versus-fresh-approval sequencing required correction. | ISR-01, UX/requirements, rejection/full-chain UAT and inert accessible rendering. |
| 13. Are host/database/secrets/broker/model/data/network outages handled? | Each has a fail-closed or explicitly degraded state; NAS is asynchronous. Key availability, restored outbox and in-flight orders require drills rather than optimistic recovery. | Operations/RISK_MODEL outage matrices, TM-17 through TM-27, conditional RPO/RTO and human re-arm. |
| 14. Can unnecessary complexity be removed? | Yes: one modular product core, four hard-stop scopes, one active order/account, no broker OAuth/live route, no per-specialist microservices, no extra queue/vector store/HA. | Keep security-sensitive process identities; removing those would remove a needed authority boundary. |

## Residual risks requiring explicit decisions

Human decisions remain: key recovery custodians and realistic operator coverage; the shared local Ubuntu development host exposure/encrypted volume changes; independent security-sensitive human review; private identity/recovery choice; proposed capital/risk/benchmark/fallback parameters; export disclosure and evidence rights; and future live/commercial deployment/key/audit isolation. A qualification spike must select and prove database tenant-context enforcement and a supported TDE/identity/backup combination.

Residual hazards include host-root compromise, execution-token theft outside app controls, plausible research poisoning, unretained licensed evidence, insufficient forward samples, shared-host contention and catastrophic key loss. These are recorded limitations/gates, not findings waived through paper-mode labels. No production code, real credentials or live capabilities were added by this review.

## Review disposition

The five identified documentation findings are corrected; no open Critical/High design contradiction was found in this review after re-reading the changes. Recommend presenting the DRAFT design for human review once main-agent completion validation passes. This is not operational risk acceptance: tenant-context, TDE/restore, broker semantics, host capacity and every runtime control remain unproved implementation gates. Do not describe Design Gate 1 as human-approved. No implementation, service setup, credential provisioning, merge or live-trading authority follows from this review.
