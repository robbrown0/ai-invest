# PostgreSQL V0 runtime — independent security review

Scope: the fixed native process guard, digest-based PostgreSQL image, local-key bootstrap and protected recovery-copy helper. The reviewer did not implement these controls. This is private single-host PAPER development under the owner's explicit local-key-provider approval, not LIVE, production, OpenBao or Gate 2 approval.

## Disposition

The reviewed native guard and fixed bootstrap operations may proceed within this narrow development scope. No generic privileged runner, global host-policy change, external database listener or brokerage connectivity is introduced. Runtime evidence, actual application database tests and final regression results must be reported separately from this source review.

- The native constructor rejects unsupported identities; sets no-new-privileges, non-dumpable state, zero soft/hard core limits and restrictive umask; and requires bounded memory, CPU and tasks plus effective swap maximum/current of zero. The parser refuses malformed, unlimited and overflowing values. The container's private cgroup namespace must expose its own cgroup at the fixed read paths. These checks precede application entry, but do not protect against trusted root/kernel interference or code intentionally removing its protections.
- Every secret-reading native executable must load the fixed image-owned preload. `LD_PRELOAD` presence alone is insufficient: a loader may warn and continue if a library cannot load. The protected probe and helper's direct `ai_guard_status()` call exercise the actual symbol; PostgreSQL process metadata checks supply additional evidence. Only fixed trusted images/configuration are supported; a caller-selected preload is not authorized.
- Forked PostgreSQL workers inherit non-dumpable/core restrictions. Executable transitions rely on the constructor running again. The native crash probe checks child termination and absence of the core status flag; it is not an independent forensic collector-retention proof. The prior finite observer milestone is not silently extended to every database/helper process.
- Bootstrap performs only fixed non-secret SQL labels and fixed migration files, with bounded subprocess duration and captured command failures. No key bytes are returned by SQL. Initial WAL-off bootstrap must contain no application data; final WAL encryption must be enabled and verified before migrations/application use. Unexpected partial initialization is preserved rather than reset or overwritten.
- Recovery copies are read and byte-compared only inside the protected helper. Source and destinations are fixed; the source is a bounded regular single-link service-owned file, targets are exclusive-created mode0600, and file/directory writes are synchronized. Root-only mount ancestors and no concurrent key rotation remain assumptions. A partial failure must preserve existing copies and must not trigger blind overwrite/retry. Separately mounted on-volume copies are not independent disaster recovery; protected offline custody remains necessary.
- PostgreSQL runtime checks inspect process metadata only within the container, not key material. Root ownership of protected `/proc` entries is a non-dumpable-state indicator, not a direct `PR_GET_DUMPABLE` call in each server worker. Do not overstate this or claim it qualifies future credential-bearing services automatically.
- Tenant application roles must remain non-owner, non-superuser, non-BYPASSRLS and without role memberships. Session-user ownership mappings are not caller-supplied tenant GUCs. Runtime grants must exclude identity writes, DDL and audit mutation.

The subsequently reviewed synthetic application follows those role constraints: two fixed peer-authenticated service identities, socket-only/no-network application containers, no key or database-file mounts, and exact `Workflow` type pairs that cannot attach an Alpaca adapter. The broker fixture commits acceptance in a separate PostgreSQL transaction so an application exit can leave a durable UNKNOWN order without losing broker-side acceptance. Its third migration retains TDE, FORCE RLS, composite tenant/account references and bounded state. Role/access-denial observations now require SQLSTATE42501 rather than counting arbitrary API errors as successful rejection; cross-tenant GUC spoofing cannot replace `session_user` identity.

The storage validation uses a fixed public synthetic marker, SQL decryption and four encrypted probe relations (heap/index/TOAST), with bounded raw-page checks inside the protected helper. A finite WAL interval decodes with pg_tde keys and refuses without them. This supports the specific tested data/WAL paths, not a claim that every cluster catalog is TDE-encrypted. A database restart plus durable broker/application reconciliation is not a full cold backup/restore exercise. Local key recovery copies are not offline disaster-recovery custody.

## Findings and evidence

The implementation author found and corrected a native GLIBC-symbol compatibility failure before key generation by using a bounded manual integer parser. A permanent regression is required. Review additionally requested source-identity checks during recovery copying and prevalidation of both targets. The revised helper now opens sources/targets relative to no-follow directory descriptors, checks both destinations before reading/copying, and verifies source identity/size/mtime/ctime after copying. Those corrections were independently inspected and approved for the fixed protected recovery operation. A failure after one successful copy still preserves that copy and refuses blind replacement. No privileged setup, database migration, key generation or protected file-content access was performed by the reviewer.

The reviewer independently ran both C syntax checks (`-std=c11 -Wall -Wextra -Werror`, library and probe variants) and the then-current **86 V0 tests: PASS**. These tests do not by themselves exercise the new protected runtime. The implementation author's container probe and subsequent database/recovery results belong to deployment evidence, not independent reruns.

Final independent rerun: **101 V0 tests and 282 preserved qualification tests, 383 total: PASS**, plus `git diff --check`. The 15 new tests include native ABI-symbol checks, fixed seed/state compatibility, SQL/package version distinction, recovery-copy fixtures and sanitized failure handling. An initial offline seed test erroneously read the container-only migration path; its fixture was corrected before the passing rerun. Mocks and ordinary temporary files do not constitute additional protected runtime trials. The reviewer did not repeat the author's database restart or inspect key material.

Final disposition: no blocking issue remains for the demonstrated **PostgreSQL-backed disconnected synthetic** milestone. The small build script performs trusted-checkout image builds only; the readiness command reports database connectivity without claiming PAPER execution is ready. Killing a Docker CLI on timeout does not itself prove the container worker is terminated: a bounded whole-worker lifecycle remains required before real credential-bearing execution. Actual PAPER provisioning/transport/order wiring and independent recovery custody are not approved or claimed complete by this review. Both existing qualification authorization flags remain false.
