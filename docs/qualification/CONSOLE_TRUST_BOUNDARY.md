# Physical Console Trust Boundary — Non-Secret Qualification

**Status:** Proposed host policy; NOT INSTALLED by agents; Gate 2 NOT PASSED.
**Date:** 2026-09-09. **Scope:** Synthetic metadata only, no secret-input path or bootstrap.

## Confirmed failure and design correction

Human-observed, immediately adjacent commands at the physical console returned `tty` = `/dev/tty3` and `sudo tty` = `/dev/pts/3`. The prior diagnostic returned `failed_checks: ["tty_identity"]`, `checks_passed: false`, `secret_entry_authorized: false`, and `runtime_crash_suppression_qualified: false`. No project secret was entered. This confirms sudo PTY allocation, not an unidentified metadata failure. The original design mistakenly assumed privilege elevation preserved the direct VT; the implemented rejection was correct. Historical generic failure, wrapper and diagnostic reviews are retained unchanged, not retroactively claimed successful.

Routine application use, administration, development, monitoring and normal running-service restarts remain SSH/private-LAN workflows. Rare high-trust secret bootstrap, encrypted cold-start recovery, break-glass and sensitive rekeying may require physical presence. A cold reboot that seals OpenBao or locks storage can require such recovery; that does not mean every application restart requires a console. This metadata command grants no standing application authority.

## Alternatives and selection

| Alternative | Assessment | Disposition |
| --- | --- | --- |
| A: command-specific sudo PTY exception | Standard password authentication, exact command/argument/digest, no transferable authorization, minimal removable policy. Requires root-owned immutable executable ancestry, correct effective policy and current local-session checks. | Provisionally selected for the exact `--diagnostic` command only; human runtime proof still required. |
| B: pre-sudo authorization artifact | An unprivileged file, even mode 0600 and UID/host/boot/TTL-bound, is forgeable by another same-UID SSH process. Symlink protection, atomic consume and timestamps cannot authenticate its issuer. Root-authenticated issuance recreates a broker; custom crypto adds key custody. | Reject for V0. No artifact is minted, consumed, cached or replayable. |
| C: fixed systemd unit | Fixed ExecStart and resource controls are useful, but start authorization still needs sudo/PAM/logind. Detachment alone does not prevent terminal/journal capture; secret input routing and unit credentials need separate design. | Retain existing bounded scope, not a new daemon/unit authorization subsystem. Revisit future secret worker only after this checkpoint. |
| D: standard privilege broker | Sudo/PAM plus logind corroboration suffice for this experiment. Polkit or a custom daemon would add policy/session complexity without independently authenticating physical keyboard intent. | Use sudo with logind corroboration; no new daemon, PAM changes or custom cryptography. |
| E: direct root console login | Adds a root authentication credential and broad root session exposure; recovery/audit burden exceeds a single exact-command exception. | Reject; root login remains unchanged. |

The selected path is direct VT login -> standard fresh sudo/PAM authentication -> exact reviewed root-owned diagnostic -> root-side kernel VT, login UID, enrolled-host and active local logind checks -> fixed systemd/unshare scope. Instead of carrying a caller-created assertion across sudo's PTY, the exact-command policy preserves the kernel terminal association. The old direct VT checks are NOT removed. The privileged process need not universally have a VT in other designs, but preserving it is the simplest proposed mechanism here.

## Exact privilege scope and local syntax evidence

Installed sudo and visudo are **1.9.15p5**, sudoers grammar **50**; systemd/loginctl **255**, Python **3.12.3**. Local manuals `/usr/share/man/man5/sudoers.5.gz` and `/usr/share/man/man1/loginctl.1.gz` were read. Installed `visudo -c -s -f infrastructure/qualification/ai-invest-operator.sudoers` returns `parsed OK` without root or host-policy installation. That is actual parser evidence, not installed-policy behavior. Online versioned manual fetches were unavailable; installed version-matched documentation is the primary authority for this proposal.

The [policy template](../../infrastructure/qualification/ai-invest-operator.sudoers) binds numeric operator UID 1000, run-as root:root, exact installed path, exactly `--diagnostic`, and SHA-256 of the reviewed wrapper. No wildcard, empty argument form, internal scoped mode, alternate executable, shell or bootstrap grant exists. Existing administrator permissions are not revoked by a narrower additional rule; this is not containment of an existing root administrator.

Only matching command defaults disable `use_pty` and sudo input/output recording. `authenticate`, `PASSWD`, zero timestamp timeout and no exempt group require fresh authentication under the proposed policy. `NOSETENV`, environment reset with empty keep/check lists, fixed secure PATH, root HOME/logname, closed descriptors from 3 upward, and restrictive umask prevent caller configuration from steering execution. Safe fixed command audit records remain; this non-secret command never requests a project secret. No global defaults, sudoers edits, swap/crash/Docker changes or NOPASSWD grant are proposed.

Command-specific Defaults apply to any user whose command matches; they cannot simultaneously be user-scoped. Therefore the wrapper additionally requires sudo's invoking UID/name, the kernel audit login UID and current logind session UID to match the fixed operator. These are corroborating checks, not proof against root fabricating a process. `loginctl show-session self` examines its own inherited login session before scope migration; `auto` is prohibited. Require active, unlocked, non-remote, class=user, type=tty, service=login, matching actual VT. Missing fields, duplicates, unknown fields, stale/closing sessions or PAM moving the command outside that session fail closed. No session identifiers/metadata are published.

The script uses command-scoped `fdexec=never`: sudo's default digest execution through `/proc/self/fd/N` conflicts with the existing canonical `__file__` guard. The digest is NOT a substitute for root-owned, single-link, non-symlink executable and non-writable ancestry. An unprivileged caller cannot replace those installed bytes. Concurrent root replacement remains a trusted-administrator TOCTOU risk: prohibit updates during any run, check installed hashes, and do not claim protection from malicious root. Checkout bytes can only veto pinned installed code, not supply arbitrary root code. Standard interpreter/system binaries and host root/kernel remain trusted. This is host-specific qualification infrastructure, not portable application policy.

No bearer authorization is carried into the scope. A root parent launches the fixed child with only the already-existing result inode identity; that identity is not a privilege token. Replays/new invocations require current session checks and fresh sudo authentication; stale cached sudo authentication must not suffice. After reboot there is no project authorization token to reuse. Actual policy/PAM timing and reboot behavior remain untested; unit tests of fake tokens would not prove them.

## Threat limits that must not be concealed

Kernel controlling-TTY, all three VT descriptors, login UID, local active logind session and fresh password authentication resist ordinary SSH/GUI/tmux/screen initiation and reopened VT-descriptor disguises. Environment markers remain additional rejection signals, not the security boundary: sudo may strip them. Unexpected retained environment is rejected; permitted values are then discarded for a fixed clean environment. SSH cannot gain a local session merely by forging SUDO_* or environment variables.

An already compromised authorized physical login, hostile PAM/interpreter/kernel, keylogger or host root can undermine human intent. No software TTY test attests a physical keyboard against all same-UID compromise. Observed `dev.tty.legacy_tiocsti=0` and `kernel.yama.ptrace_scope=1` help, but do not close that gap. Stronger assurance against an already compromised console account would require a separately trusted recovery environment/hardware-authentication decision; do not generate real secrets on the strength of this proposal. Recovery custody remains one human, not multi-person separation.
